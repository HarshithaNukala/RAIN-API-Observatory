## 1. Features implemented

- **Automatic incidents:**
  - A check that takes a monitor to DOWN opens an incident, recording its trigger check.
  - Repeated failures add nothing while an incident is active.
  - The incident resolves automatically once the recovery threshold of consecutive passing checks is reached. Slow passes count.
  - A later outage opens a new incident.
- **Owner actions:** acknowledge OPEN incidents, and edit the title, description and severity.
- **Timeline:** permanent and append-only (CREATED, ACKNOWLEDGED, RESOLVED, UPDATED), written in
  the same transaction as each change.
- **API:** list with filters and pagination, counts, details, timeline, acknowledge, update.
- **Web:** the incident dashboard and list, incident details with timeline, and incidents shown on monitor pages and in the main navigation.

## 2. Database migrations

`0005_incidents` (generated by drizzle-kit, plus a hand-written trigger). Migrations 0000–0004
are unchanged.

**`incidents` table:**

- Columns: monitor and owner (cascade), title, description, severity (default **HIGH**), status, the started, acknowledged and resolved timestamps, `acknowledged_by`, and the trigger and resolving check IDs. The check IDs deliberately have no foreign key, so check history can expire.
- CHECKs: valid status and severity; status consistent with its timestamps; non-blank title; description length.
- Indexes:
  - partial **unique** `(monitor_id) WHERE status <> 'RESOLVED'`;
  - owner/started keyset;
  - owner/status;
  - monitor/started.

**`incident_events` table:**

- Columns: incident (cascade), type, actor (NULL means the system), `occurred_at`, a generated description, and the check ID.
- Index on timeline order.
- Partial unique `(incident_id, event_type, check_id)`.
- A `BEFORE UPDATE` trigger rejects every UPDATE.

Both tables have RLS enabled with no policies, like the existing tables.

## 3. Incident lifecycle and recovery rules

- **Where it runs:** inside the existing completion transaction, after the check insert, with the monitor row locked and the active incident locked. The decision is the pure function `planIncident`.
- **Opening:** the new health is DOWN and no incident is active.
- **Resolving:** an incident is active, and this passing check brings consecutive passes to the recovery threshold.
- **Defaults** (failure 2, recovery 2):
  - The first failure opens nothing.
  - The second failure opens the incident.
  - The first pass after the outage gives DEGRADED, and the incident stays open.
  - The second pass resolves it, leaving HEALTHY, or DEGRADED if slow.
  - Any failure resets the count.
- **Never affects incidents:** health-neutral refusals (SSRF, configuration) and checks recorded while the monitor is paused.
- **Races:**
  - Two workers can't both open an incident: the row lock serialises them and the partial unique index backs it up.
  - Duplicate attempts stop at the check's `ON CONFLICT`.
  - A crash or error rolls back the check, the incident, the event and the health change together.
  - Acknowledgement and resolution serialise on the incident row, without deadlocks.

## 4. API endpoints (`/api/v1`, authenticated, owner-scoped)

- `GET /incidents` (`status`=OPEN|ACKNOWLEDGED|RESOLVED|ACTIVE, `severity`, `monitorId`, `limit`,
  `cursor`) returns `{ items, nextCursor, total }`.
- `GET /incidents/counts` (optional `monitorId`).
- `GET /incidents/:id`
- `GET /incidents/:id/events` (oldest first, paginated).
- `POST /incidents/:id/acknowledge` returns 409 `INCIDENT_ALREADY_ACKNOWLEDGED` or 409 `INCIDENT_ALREADY_RESOLVED` when not allowed.
- `PATCH /incidents/:id`: a strict schema accepting `title`, `description` and `severity` only.

## 6. Security and ownership

- Every repository statement filters by `owner_id`; timeline queries go through an owner-checked subquery.
- Another user's incident, an unknown ID and a malformed ID all return the same 404 `INCIDENT_NOT_FOUND`.
- All inputs are validated with Zod. PATCH can't set the status, the timestamps or any system field.
- Timeline rows can't be modified: no endpoint does it, and a database trigger rejects UPDATEs.
- Responses contain no monitor URL, headers or bodies.
- Event descriptions are generated and don't echo the owner's text.
- Database errors are returned as a generic 500.

## 9. Known limitations

- Severity is fixed at HIGH on creation; there is no per-monitor default.
- There is no manual resolve or reopen; resolution is automatic only.
- Events for one incident in the same millisecond are ordered by ID.
- Deleting a monitor deletes its incidents, following the existing ownership cascade.
- There is no retention for incidents or checks.
- Acknowledgement is single-user (the owner); there are no teams yet.
- Not done, by design, because they belong to later phases: notifications, analytics, status pages.
- Carried over from Phase 3:
  - a configuration edit during an in-flight check doesn't invalidate that check;
  - checks run at least once.
